# The pitch coefficient-split hoist — done, and the saving is smaller than projected

Date 2026-08-03 (Opus 5). Continues the task CLAUDE.md left as "OWED NEXT".

## What was done

`eb_pitch_eval` used to be handed a **row pointer** (`const double *tab`). A
pointer to a row cannot be turned back into a row **index** — `juno_pitch_table`
is `static` per translation unit — so the fast build could not index a pre-split
coefficient table and had to split each coefficient at use, in soft-double, on
the per-sample path.

The API now takes the CV and reads its own row:

```c
float eb_pitch_eval(float cv, float gain);      /* was (cv, tab, gain) */
```

`engine_b/eb_pitch_tab.h` (generated by `tools/engineb/gen_pitch_tab.c`, C99 hex
float literals, no decimal round-trip) carries the 29×13 split as build-time
constants.

**The generated table is checked, not trusted.** `eb_pitch_tab_selfcheck()`
re-derives every pair with `df_coef` — the arithmetic the table replaces — and
`engine_b/tests/test_pitch_tab.c` requires bit equality:
**0 of 377 pairs differ.** If the table is ever regenerated from a changed
`juno_pitch_table` and drifts, that test goes red.

## The result — soft-double is gone from the hot path

S3 relocation census (`xtensa-esp32s3-elf-gcc -O2`, MEASURED):

| build | soft-double calls per `eb_pitch_eval` |
|---|---|
| default (double) | 23 `__muldf3` + 14 `__adddf3` + 2 `__extendsfdf2` + 2 `__fixdfsi` + 1 `__truncdfsf2` |
| **EB_PITCH_FAST=1** | **none on the per-sample path** (the 2 remaining relocs are inside `eb_pitch_tab_selfcheck`, which only the unit test calls) |

Gates, both PROVEN this session:

| gate | result |
|---|---|
| default build, `null_b --module pitch` | EXACTLY 0 (bit-exact, unchanged) |
| `JUNO_EB_PITCH_FAST=1`, all 30 scenarios | PASS, worst global **−123.6 dB** |
| whole engine `--module all` | EXACTLY 0 |
| vs the PLUGIN at 48 kHz | 11/11 BIT-EXACT |
| all 7 unit tests | PASS |

The fast-build residual is **bit-identical to the pre-hoist −123.6 dB**, which is
the proof the hoist moved *where* the split happens and not the arithmetic.

## THE SAVING IS 22 %, NOT THE ~65 % PROJECTED. Correcting the record.

STATIC Xtensa instruction counts per call (MEASURED, `objdump`):

| build | body | helper bodies | **per call** |
|---|---|---|---|
| default (double) | ~230 | 4,228 in libgcc soft-double | **~4,450** |
| **EB_PITCH_FAST=1** | 324 | 2,802 in df helpers | **~3,126** |

CLAUDE.md's handover implied that removing soft-double removes the block's cost.
**It does not.** The compensated double-float arithmetic that was needed to pass
the −100 dB gate costs nearly what soft-double costs. Per sample (8 voices):
**27,351 → ~21,300 instructions, a saving of ~6,000, not ~20,000.**

### Why — measured, not guessed

Forcing `always_inline` on the df helpers makes it **worse**: 3,452 instructions
inlined against 3,126 as calls. The mnemonic mix of the inlined build says why:

| mnemonic | count |
|---|---|
| `lsi` (float load) | 1,254 |
| `ssi` (float store) | 423 |
| `sub.s` / `add.s` / `mul.s` (real arithmetic) | 1,635 |

**1,677 of 3,452 instructions are spill traffic.** The LX7 has 16 float
registers; compensated double-float keeps far more values live, so inlining
converts call overhead into spills and loses. The helpers are therefore left as
calls, deliberately, with that measurement recorded in the source.

## What this means for the S3 verdict

Whole chain was ~71,000 instr/sample. After this fix: **~65,000**, against a
~9,500 two-core budget — about **6.8× over**, not the ~4.6× the handover
projected.

**The next idea is a redesign, not a tuning.** The gate failure that forced this
precision was a *pitch error integrating in the phase accumulator*. The fix was
applied to the polynomial — 13 terms, 8 times a sample. It may belong instead in
the **DCO's phase accumulator**: carry the phase in double-float and the
polynomial in plain float. That is one compensated add per sub-sample against a
whole compensated polynomial per sample, and plain float pitch already exists
(it failed only through integration). It must be built and gated like everything
else; it is a hypothesis with a measured motivation, not a plan.

## Also found: the QEMU harness cannot measure short spans

Two runs of the harness differing only in `EB_PITCH_FAST` disagree by exactly
500,000 or 1,000,000 raw counter units on functions that **did not change**
(chorus 302,276 vs 1,302,275; env 1,170,920 vs 2,170,433). Those are fixed
integer offsets, not noise.

Cause: CCOUNT under `-icount` advances 25 instructions at a time, and QEMU
updates it at translation-block boundaries. A span of tens-to-hundreds of
instructions therefore samples the counter's quantisation systematically, and
changing code layout moves the block boundaries. **Per-call figures from this
harness are not trustworthy**, including the per-function table in
`docs/engineb/data/qemu_instr_counts.md` — that table's numbers should be read
as ±25 instructions per call at best, and its `dco_step4` and `pitch` entries
disagree with the static census by 20–60 %.

What the harness IS good for: `sample_total`, a span of ~70,000 instructions
where quantisation is negligible. Static `objdump` counts are the reliable tool
for per-function cost, and they are what this page uses.
