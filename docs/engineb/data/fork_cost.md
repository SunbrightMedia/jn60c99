# The fork's real cost, and the root cause of the S3 crash

MEASURED 2026-08-07, host x86, callgrind, zero-block baseline subtracted.
Harness: `tools/engineb/fork_cost.c` — it drives the two calls the S3 firmware
drives, `eb_engine_render_voices()` and `eb_master_render()`, on the frozen
coefficient blob, with the at-rest flags cleared for N voices.

## 1. THE ROOT CAUSE OF THE HARDWARE CRASH — a layout mismatch, not a DSP bug

The fork build segfaulted on the host at `eb_dco_wt.c:508`, the same fault the
S3 board showed as an MMU entry error. Memcheck named it in one run.

|                              | bytes   |
|------------------------------|---------|
| `eb_render_state`, trunk build | 735,332 |
| `eb_render_state`, fork build  | 736,744 |
| voice prefix copied from blob  |   6,808 |
| `offsetof(wt)` in the fork     |   3,016 |

`s3_listen.bin` was generated by a TRUNK-layout build. The firmware copies
6,808 of its bytes into a FORK-layout struct, so trunk bytes land on the
wavetable state, `rpos` becomes a wild index, and the ring read leaves the
mapped region.

**The firmware's own layout check cannot fire.** It compares the blob's header
word against `S3L_VOICE_SZ` — and both are written by the SAME generator run.
It verifies the header against itself and says nothing about the struct the
firmware actually compiled. This is the catalogued defect class: a check that
has never been seen to fail is not a check.

FIX OWED (not done here): regenerate the blob under the firmware's own flags,
and make the check compare against `sizeof` in the consuming build.

## 2. THE COST

6 voices + full FX, 44,100 Hz, instructions per sample:

| build                          | x86 instr/sample |
|--------------------------------|------------------|
| port trunk, 8 voices (earlier) | 30,471           |
| engine B, trunk arithmetic     | 16,924           |
| **engine B, FORK**             | **13,792**       |

The fork flags are `EB_FORK_S3 EB_DCO_WT=1 EB_LFO_SHARED=1` — recentered pitch,
the fork exp, the band-limited wavetable DCO, one shared LFO.

**Where the cost now is, and it is not where it was:**

| module            | instr/sample | share |
|-------------------|--------------|-------|
| `eb_vcf_substep`  | 1,936        | 13.6% |
| `eb_vcf_tick`     | 1,819        | 12.7% |
| render plumbing   | 1,627        | 11.4% |
| `eb_vca_tick`     | 1,142        |  8.0% |
| `eb_dco_wt_tick`  | 1,090        |  7.6% |
| `eb_env_tick`     |   960        |  6.7% |
| `eb_pitch_fork_eval` | 599       |  4.2% |

Pitch was 43 % of the trunk engine. It is **4.2 %** of the fork. The VCF is now
the largest item at 26 %, and it is the next lever if one is needed.

## 3. WHAT THIS SAYS ABOUT TARGETS

At the MEASURED ARM/x86 static ratio of 0.77 (`arm_cost.md`), the fork is
**~10,620 ARM instructions/sample**.

| target                       | budget cyc/sample | IPC needed |
|------------------------------|-------------------|------------|
| Daisy Seed (M7 480, SDRAM)   | 10,884            | 0.98       |
| Teensy 4.1 (M7 600, TCM)     | 13,605            | 0.78       |
| Pi Zero 2 W, ONE A53 core    | 22,676            | 0.47       |
| Pi Zero 2 W, four A53 cores  | 90,703            | 0.12       |

**NOT MEASURED: the IPC of any of these chips on this code.** The one ARM IPC
this project owns is the Daisy's 0.25, measured with the engine in SDRAM. The
Teensy 4.1 row is the interesting one precisely because its 512 KB of
tightly-coupled RAM is single-cycle and removes the memory stall that produced
that 0.25 — but that is an argument, not a measurement, and this project has
been wrong about unmeasured performance twice.
