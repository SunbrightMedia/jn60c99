

## CRITIQUE 1 — verdict BROKEN

BROKEN. Three of the design's load-bearing structural claims are refuted by measurement I ran against the repo's own code, and two of them are fatal to the instrument rather than to the gate.

(1) WARM RECALL IS NOT COLD RECALL — MEASURED. The gate's 384 cases each recall from a fresh baked boot image. The device, from Step 2 onward, recalls on top of the previous patch. Running the port's own recall at 44,100 with the shipping fork flags over 64 consecutive patch pairs (A then B, vs B alone): eb_render_coefs DIFFER in 24 of 64, eb_master_coef in 41 of 64, the cell array in 41 of 64 (worst 144 bytes). The stale cells are the routing-dependent FX blocks — 102528+, 4297xxx, 6497xxx, 10692016..10693216 — i.e. exactly the slot-1-routing fine-FX family CLAUDE.md already documents (TYPE 1 -> 4297xxx, TYPE 5 -> 6497xxx + 10693xxx). Consequence: section 4.3's device gate compares the board's WARM coefficient CRC against the host's COLD CRC, and section 4.4's rule is "COEF CRC != host -> MUTED". Step 2's own exit test ("all 64 CRCs match the host") cannot pass on hardware, and the failure will read as an Xtensa float defect. Evidence: scratchpad/refute/warm.c, warm2.c (both build and run).

(2) THE CELL ARRAY CANNOT HOLD PER-VOICE STATE, SO NO VOICE ABOVE 0 CAN PLAY A NOTE. I ran the design's own ebdev_at over the cells eb_render_state_seed and eb_render_events_mirror actually read. Every per-voice cell except the five scatter offsets returns MISS: cell 320 (gate), 2592/2624/2640/2672/2720 (env), 9712..10512 (VCA), 7520..7568 (res), 560..1104 (glide), 1488..1600 (LFO), for v=1..5. Cell 320 is not a recall cell — eb_render.c:484-488 reads st->gate_cell320[v] per voice on the audio path as the ADSR gate, and its only source is the cell array at v*10512+320. The firmware says this itself: juno_s3_listen.c:262-270 "without it there is no note ... the gate cells live in state, not in coefficients", and :1126 "with coefficients alone the note does not release at all, measured". Under the design's own ebdev_trap rule that is six hard mutes on the first chord.

(3) eb_render_events_mirror IS ON THE RECALL PATH. Risk R5 says it is not. Both existing shims call it inside the same `if (EB_GEN_SEEN != eb_coef_gen)` block as eb_render_coefs_build (shim/voices/juno_driver.c:225,228; shim/standalone/juno_driver.c:361). It reads per-voice cell 320 (unmapped for v>0), it WRITES into the cell array (*(float*)(base+aux)=0.0f, eb_coefs.c:375 — refuting the "cell array is a write-only input nobody listens to" model that the whole double-buffer argument rests on), and it does memset(s->dco_live_seeded,0,...) whose own comment (eb_coefs.c:381-383) says "a coefficient rebuild must invalidate it or the voice keeps last patch's non-pitch DCO fields". The pump in 3.5 has no such step and publish is a bare pointer swap.

Several of the design's boldest claims survived my attack and I say so below — the fold, the flash figure, the absence of libm, the memory fit, and the shared-LUT premise are all correct.

### FATAL
- WARM != COLD RECALL, MEASURED, 24/64 and 41/64. The 384-case gate recalls every patch from a fresh boot image; the device recalls on top of the previous patch. Over 64 consecutive factory pairs at 44,100 with -DEB_FORK_S3 -DEB_LFO_SHARED=1 -DEB_VCF_RES_LUT=256 -DEB_NUM_VOICES=6: eb_render_coefs differ 24/64, eb_master_coef differ 41/64, cell array differs 41/64 (worst 144 bytes). Pair 4->5 renders render_coefs differing at byte 14012 and master_coef differing in 71 of 1704 bytes; pair 21->22 differs in 136 of 1704. The stale cells are the FX routing blocks (102528, 4297584..4297988, 6497168..6497508, 10692016..10693216) — patch A writes a slot-1 fine-FX cell, patch B's arm never clears it, and eb_master_coefs_build reads it unconditionally. So (a) the device CRC gate in 4.3 compares warm against cold and mismatches, (b) 4.4's rule mutes the instrument on the second patch change, and (c) the sound of a patch genuinely depends on which patch preceded it in 24 of 64 cases. The design has no warm case anywhere. Repro: /tmp/claude-0/-home-user-jn60c99/851980e2-931d-52da-bb74-16fb8562b242/scratchpad/refute/warm.c and warm2.c.
- PER-VOICE STATE IS UNMAPPED — THE ARRAY CANNOT SUPPORT A NOTE ON VOICES 1..5. I ran the design's own segment table and voice>0 branch over the cells the engine actually reads. Mapped for v=0, MISS for v=1..5: cell 320 (gate), 2592/2624/2640/2672/2720 (env1/env2), 6896/7088/7168 (cv), 9712/9776/9856/9904/10096/10128/10432/10480/10496/10512 (vca), 7520/7536/7552/7568 (res), 560/656/672/688/704/880/1104 (glide), 1488/1504/1536/1568/1600 (lfo) — all read by eb_render_state_seed at eb_coefs.c:327-350 with a1 = base + v*10512. Cell 320 is the one that is fatal at runtime rather than only at boot: eb_render.c:484-488 reads st->gate_cell320[v] every sample as the per-voice ADSR gate, and eb_render_events_mirror re-reads it from the cell array on every rebuild. The firmware already states the constraint in its own words at esp32s3/main/juno_s3_listen.c:262-270 ('without it there is no note ... the gate cells live in state, not in coefficients') and :1126 ('with coefficients alone the note does not release at all, measured') — which is why today's firmware ships TWO full 8,488-byte voice-state snapshots per note instead of driving events. The design's Steps 2, 3 and 4 all presuppose an instrument that can play, and the array it specifies cannot represent one.
- eb_render_events_mirror IS ON THE RECALL PATH AND MUTATES THE CELL ARRAY. Risk R5 asserts the opposite. Both existing shims call it in the same generation-guarded block as the coefficient build — engine_b/shim/voices/juno_driver.c:225 and :228, engine_b/shim/standalone/juno_driver.c:361, immediately after eb_render_coefs_build/eb_master_coefs_build. Three consequences the design does not carry: (i) it reads CF(a1,320) per voice, which is unmapped for v>0; (ii) it executes *(float *)(base + 101504 + 32v) = 0.0f at eb_coefs.c:375, so the cell array is read-write on the event path and the section 3.1 argument ('a half-written cell array is not being listened to; only the publish must be atomic') is unsound as stated; (iii) it clears dco_live_seeded, and eb_coefs.c:381-383 says why: 'the DCO's live coefficient copy is seeded from the recall coefficients, so a coefficient rebuild must invalidate it or the voice keeps last patch's non-pitch DCO fields.'
- CONCRETE HALF-RECALLED STATE, TRACED, FROM THE DESIGN'S OWN PUMP. Take a patch change from a saw+sub patch to a pulse patch. eb_recall_pump walks RCL_CELLS -> RCL_VOICES x6 -> RCL_MASTER -> RCL_READY, then publish swaps RC_ACTIVE. Nothing in that sequence clears st->dco_live_seeded[v]. eb_render.c:653-656 seeds st->dco_live[v] = c->dco[v] once and never again, so after the swap the envelopes, VCF, LFO and master all move to the new patch while the DCO's waveform mix, sub level and PWM stay on the OLD patch until the next note event happens to run events_mirror. That is a bisected instrument on every program change, it is audible, and it is a defect the design introduces rather than one it inherits. A second, independent half-recall follows from 3.5 as written: eb_recall_param() re-runs one BINDINGS row into the SHARED cell array while the pump may be part-way through reading that array for the previous change (one voice per block, up to 8 blocks = 46.4 ms). Two encoder detents inside 46 ms is ordinary playing. Voices 0..2 then build from the old cell value and voices 3..5 from the new — a cutoff or detune split across the chord, with no interlock anywhere in the design.

### OPTIMISTIC
- 'The mechanism is BUILT and GATED ... device recall works, and it is now PROVEN and not estimated.' The gate builds BOTH sides with the same host compiler from the same sources; the only difference between gate_host and gate_dev is the address map (host/gate_host.c gathers the 12 MB array into the device layout; dev/gate.c passes a bogus ST=(unsigned char*)1 and redirects JF/JI to ebdev_at). So the 384-case result is a complete and genuinely good proof that the 31-segment rebase is correct and complete for cold recall — and a proof of nothing whatever about the device. Section 9 concedes this; the headline sentence and the Step 0 'Done: this session' do not.
- 'The port's own unmodified recall code' / 'Do not propose trunk changes'. The design's own artifacts modify the trunk: src/juno_engine.h:39-40's JF/JI macros are replaced with ebdev_at calls, and delay_recall.c, reverb_recall.c, effect_modes.c and juno_driver.c are edited for the 17 raw casts. That is survivable behind #ifdef EBDEV, but juno_engine.h is compiled by every port-side gate in make verify, and the design should say so instead of claiming verbatim reuse.
- The 6-voice memory table is not the shipping configuration. Nothing in esp32s3/main/CMakeLists.txt sets EB_NUM_VOICES=6 — line 50 sets EB_FORK_S3, EB_LFO_SHARED=1, EB_VCF_RES_LUT=256 only, and S3_VOICES maps to S3L_VOICES, a render-loop cap, not the struct. Measured with the shipping flags: sizeof(eb_render_coefs) is 18,788 at 8 voices against the design's 14,188 at 6, and s3_listen_meta.h's S3L_COEF_SZ 18788 confirms the built firmware is 8-voice. Every RAM figure in section 2 is therefore projected, not measured on the config that exists. It still fits, so this is a labelling fault rather than a fatal one.
- The resonance-LUT hoist is booked as done in two tables (10,280 bytes of RAM in section 2, and 0 instead of ~460,000 instructions in section 3.3) but it is an unbuilt change to the fork's per-sample hot path. eb_vcf_res_tick reads c->lut[i] off the same per-voice eb_vcf_res_coef pointer as the k-fields (eb_vcf_res.c:258), and the lut member is declared inside that struct (eb_vcf_res.h). Sharing one table changes the struct, the tick and every caller, and needs the third-octave sonic gate. Separately, it silently overturns a recorded finding — docs/engineb/data/res_lut.md:99 says 'CONDITION scatter makes the ~20 coefficients voice-distinct; one shared table would be wrong on five voices out of six.' My own check says the DESIGN is right and res_lut.md is wrong (see 'unread'), but overturning a recorded result should be stated as such.
- 'One pointer swap at the block boundary' is presented as free. Today RC is a single static eb_render_coefs (juno_s3_listen.c:132) that load_coefs memcpy's over IN PLACE (:260), and its address is passed to the renderer on BOTH cores — :678 and :686 on core 0, :744 through :790 in worker() on core 1. Converting to a swapped pointer requires the new pointer to be visible to core 1 at the swap instant; every other cross-core datum in that file is volatile and single-writer for exactly this reason (:415, :463-464, :474). Modest work, but not zero, and not mentioned.
- -flto is in the device build (esp32s3/main/CMakeLists.txt:49) and is not in the host gate. The design's whole standard is bit-identity between those two binaries and it never mentions the flag. Low risk — GCC does not re-associate float arithmetic without -ffast-math and -ffp-contract=off is present on both sides — but it is an unmeasured difference in the one place the design says exactness is mandatory.

### UNREAD
- MEMORY: the attack FAILS and the design is right, but for a reason it does not cite. The prompt's '~78 KB free internal' is the abandoned MIXED-ring build's number (docs/engineb/data/fx_measured.md:45, 'free internal now 64515'). fx_measured.md:76 CLOSED ring placement by measurement — PSRAM is 24 cycles FASTER, so all nine rings stay in PSRAM and about 102 KB of internal SRAM is released; boot free internal is 166,931 bytes (fx_chain_price.md:32). The design's 65,184-byte RAM subtotal fits, and so does the 74,424 the shipping 8-voice config would actually need. One caveat the design should carry: fx_measured.md:76 earmarks that same 102 KB 'for whatever the two-chip link turns out to need', so recall and the link are now competing for one pool.
- THE 4-INSTRUCTION FOLD IS REAL — I reproduced it independently. I regenerated a literal binary-search chain from the design's own 31-segment table and compiled it with xtensa-esp32s3-elf-gcc -O2 -mlongcalls -ffp-contract=off. A constant-offset read of a voice-tile cell (6736) is entry a1,32 / l32r a8 / l32i a2,a8,80 / retw.n. A constant-offset read at 10,693,072 is entry / l32r / l32i.n / retw.n. A constant-offset STORE at 4,297,792 is entry / l32r / s32i / retw.n. Four instructions each, exactly as claimed, for both the tile and the deepest segment. The design is correct that the segment map is free at a constant site, and correct that this is load-bearing.
- NO LIBM IN THE RECALL PATH — the picolibc-vs-glibc attack fails. Zero expf/logf/powf/sinf/cosf/sqrtf/fmodf call sites in src/juno_apply.c, delay_recall.c, reverb_recall.c, chorus_recall.c, finefx_recall.c, effect_modes.c and hpf_type_lut.c. juno_curve is a clamp plus a uint32_t table punned back to float (src/juno_curve.c:18-20), so no decimal round-trip and no libm. Stage B's only transcendental is EB_EXPF inside eb_vcf_res_prepare, and EB_EXP_FORK defaults to 1 (engine_b/eb_fork_config.h:54-56), so it resolves to eb_exp_fork — pure float arithmetic (engine_b/eb_exp_fork.c) whose only libm fallback is outside [-87,88], which the LUT domain never reaches. Endianness, int width and the curve tables' uint32 representation are all non-issues for the same reasons.
- THE FLASH FIGURE IS HONEST. Built the 13 port recall objects with xtensa-esp32s3-elf-gcc -O2 -mlongcalls: 216,276 bytes total, with juno_curve.o at exactly 126,444 — the design says ~210,480 with juno_curve at 126,444. Within 3%, and the juno_curve number is exact.
- RING LENGTHS ARE NOT PATCH-DEPENDENT — an attack I expected to land and it did not. I feared a patch change would force reallocating and zeroing 6.16 MB of PSRAM rings, which would dwarf the 90,000-cycle burst and break the 'one pointer swap' claim. Measured the nine ring-length cells (6395252, 6429412, 8594772, 10691940, 10726260, 10759044, 101028, 6463716, 6496500) after juno_bank_apply for all 64 factory patches: ONE distinct set, {524288, 8192, 524288, 524288, 8192, 8192, 1024, 8192, 8192} = 6.16 MB. Repeated over the fully nibble-randomised synthetic bank the design's own gate uses: still ONE distinct set. src/delay_recall.c:397-408 writes them as literal constants. No ring churn on recall.
- THE SHARED-VOICE-TILE PREMISE IS STRUCTURALLY CORRECT AND I VERIFIED IT AT SOURCE. src/juno_apply.c:466-506 writes exactly three per-voice-distinct cells (5520 tune, 7600 fine, 10320 gain, via COND_TUNE_SCAL/COND_FINE_SCAL/COND_GAIN_SCAL), juno_apply_unison_spread writes 3968 from UNISON_3968[v], and juno_apply_lfo_tempo writes 1072 to all eight with the same value. Nothing else. So the design's five scatter offsets are complete for the RECALL path, and its correction of docs/engineb/data/res_lut.md is right: ebr_tail (eb_vcf_res.c:150-181) reads only k7856..k8192, none of which is a scatter cell, so a shared resonance table is legal. res_lut.md:99 is the wrong document, not the design.
- eb_master_state_seed's cell coverage holds even though the gate never runs it. Extracted all 351 numeric offsets in that function and tested them against the 31-segment table: 0 unmapped. A cold path the 384-case gate cannot exercise, but statically covered.
- NO SYMBOL COLLISION. engine_b/eb_dsp.c exports eb_pitch_poly / eb_triangle_wrap / eb_wrap_unit / eb_wrap_hi while src/juno_dsp.c exports juno_*, so linking the port's recall objects alongside the fork engine does not violate the standalone-link invariant the ESP32 CMakeLists relies on.
- The 17 raw-cast rewrite is exactly what the design says. Diffed the design's dev/delay_recall.c against host/delay_recall.c: the only changes are #include "ebdev.h" and 13 casts at :388-408 rewritten to ebdev_at. Faithful.

### MISSING
- A WARM CASE IN THE GATE. This is the single most important gap and it is the one that makes the design fail on hardware. The gate must recall a SEQUENCE — patch A then patch B, and A then a parameter edit then B — and compare against the same sequence on the host, not against a cold B. Given the measured 24/64 and 41/64, either the port's non-clobbering recall is the plugin's own behaviour (in which case the host reference must be the warm one and the CRC table must be per-sequence, not per-patch) or it is a defect in the port that predates this design. Which of those it is has not been established and must be, because CLAUDE.md already records one warm-recall root cause in this exact area ('Warm apply clobbered per-voice runtime').
- A DESIGN FOR PER-VOICE STATE. The array must carry, or the design must explicitly delegate, the per-voice state cells: 320 above all, plus the env/vca/glide/res/lfo blocks eb_render_state_seed reads. Either widen the tile to EB_NUM_VOICES copies of the ~40 state offsets (roughly 40 floats x 6 = under 1 KB, so this is cheap), or state that engine B's own note path replaces eb_render_events_mirror entirely and gate that replacement. Today the design does neither and the trap fires on the first chord.
- THE PUBLISH SEQUENCE, WRITTEN OUT. eb_recall_publish must specify, in order: swap RC_ACTIVE, make the pointer visible to core 1, clear dco_live_seeded, and refresh gate_cell320/aux_edge. Without the third of those the DCO stays on the previous patch. Without the fourth the note gate is stale.
- AN INTERLOCK BETWEEN eb_recall_param AND THE PUMP. The cell array is single-buffered and the pump reads it across up to 8 blocks. A second parameter change inside 46 ms corrupts the in-flight build. Either the cell array is double-buffered too (another 29 KB, still affordable at 166 KB free), or a parameter change during RCL_VOICES restarts the build from RCL_CELLS, or the pump runs to completion in one block. The design says 'if you want it faster, run the whole thing in one block' — that is the right answer and it should be the default, with the pump kept only as the fallback for a raised voice count.
- A MEASUREMENT ON XTENSA. Not one instruction of the recall path has executed on the chip. The design says this in section 9 and R3, and the mitigation (print min/max/last burst cycles on the first flash) is right. It should be Step 1's gate, not a footnote.
- THE STEP-3 'stage B alone' COST. A detent re-runs eb_render_coefs_build, which begins with memset(c, 0, sizeof *c) at eb_coefs.c:16 — 14,188 bytes at 6 voices, 18,788 at 8 — then rebuilds all six voices including the res LUT unless the hoist has landed. The design books this as 'cost is stage B alone' and tells you to measure it on the board, which is correct; it should also say that the memset alone is ~3,550 word stores and that a single-row edit rebuilding all six voices is the obvious first thing to narrow.
- THE 5 UNCARRIED PATCH BYTES ARE NOT YET IN eb_patch.h. EB_PATCH_BYTES is still 127 (engine_b/eb_patch.h:76) and eb_patch_offsets is sized by it. The design's finding — record 506 BEND GAIN, 3286/3287/3288 CHORUS PRE DELAY/LOW CUT/HIGH CUT, 3950 REVERB DENSITY — is credible and matches src/finefx_recall.c:149,173,174,175 and src/juno_apply.c:447, and it is the right kind of finding (the factory bank is constant on all five, which is exactly the blindness eb_patch.h's own header warns about). It needs the eb_patch_coverage() assertion the design proposes in Step 4 moved to Step 0, so the format cannot ship 127 by accident.


## CRITIQUE 2 — verdict BROKEN

COMPLETENESS REVIEW — device-side preset and parameter recall.

The recall half of this design is real, gated, and worth keeping. What is missing is the other half of the sentence in its own title: PARAMETER recall. The gate that produced the "BIT-IDENTICAL over 384 cases" headline is /tmp/.../scratchpad/cells/dev/gate.c, 71 lines, and I read all of it. It calls juno_bank_apply, juno_apply_unison_spread, juno_apply_condition, juno_apply_lfo_tempo(...,128.0f), then eb_render_coefs_build and eb_master_coefs_build. It never issues a note. It never calls eb_render_state_seed or eb_render_events_mirror (both declared in engine_b/eb_coefs.h:37-56). It never calls a live single-parameter edit. Every structural claim the design derives from it — including the load-bearing "the five scatter cells are the whole per-voice story, and I proved it structurally" (§1.4) — is therefore scoped to full-patch recall, and the design nowhere says so.

That scope matters because the note path writes per-voice cells that ARE coefficients. src/juno_note.c:160 writes base+304 (the note's own PITCH); :196-197 write 6864/9680 (VCF/VCA velocity); :200-201 write 1856/9824; :238/:262 arm 101504+v*32; :249 writes 320; :305 writes 592. Every one of those is read back PER VOICE by the builder: eb_coefs.c:264 (cvg_p28 = cell 304), :59 (k6864), :93 (c9824), :233 (k1856), :218 (glide k592), :352 (aux_edge), :341-352 (state). So a note-on changes coefficients, and with ONE shared voice tile every sounding voice would take the last note's pitch, velocity and gate.

1. WHICH OF THE SIX END-GOAL ITEMS THIS ADVANCES.
Genuinely advanced: item 6 (proven) — the gate exists, executes, and has a measured teeth battery including one defect it found rather than planted. Half of item 5 — preset recall, and the five-byte discovery (BEND GAIN 506, CHORUS PRE DELAY/LOW CUT/HIGH CUT 3286-3288, REVERB DENSITY 3950) is a real closure of a hole eb_patch.h's own header predicted.
Silently assumed to be someone else's job: item 5's larger half — a live parameter change. eb_recall_param() appears once, in the §1.3 file table, and is never described, priced or gated. Item 4 (seamless) — one burst is priced; no RATE is. Item 2 (exactly two boards) — §3.4 concludes "chip B cannot recall while it plays" and parks it. Item 1 (audibly identical) — no rendered audio is compared anywhere, and the per-voice CONDITION scatter / global voice index question below is an audible one. Item 3 (full FX incl. chorus) — nothing says what happens to the 6.2 MB of PSRAM rings when DELAY TYPE or EFFECT TYPE changes under a live patch switch.

2. WHAT A REAL INSTRUMENT NEEDS THAT THIS DOES NOT MENTION.
See the `missing` list — the largest items are the note path, the live-edit path with its recall-time stash (gui/juno_bridge.c:58-89 host_bpm/hpf_type/dly_*/lfo_rate_byte/last_condition), a tempo source, the edit buffer that makes patch WRITE mean the sound you are hearing, continuous controllers (bend/mod write cells 4112/7456, both inside the mod coefficient block at eb_coefs.c:40), MASTER TUNE (cell 4448, src/juno_note.c:99 "set by init; DO NOT write", and not one of the 132 bytes), the Kbd Velocity SW policy, the MODULATION family 312-317, and the encoder/LCD mapping. Also worth stating plainly: today's firmware has NO note path at all — juno_s3_listen.c:889/1001 replays captured note-on and note-off STATE snapshots at S3L_HOLD_FRAMES/S3L_REL_FRAMES. Device recall landing on top of that still cannot play a note.

3. MOST EXPENSIVE TO DISCOVER WRONG LATE.
The shape of the cell array — the single shared voice tile and the five-entry scatter set. It is baked into a generator, four generated headers, a per-rate flash boot image, the firmware's memory table, and the gate's own harness. Discovering after all of that that the per-voice set is thirteen cells, not five, and that it must be indexed by GLOBAL voice number, means regenerating every one of them. Second most expensive: the assumption that a coefficient rebuild happens at PATCH rate. It happens at NOTE rate, and §3.5's eight-block pump therefore prices note latency at 46.4 ms while calling it "inaudible as a delay".

4. IS THE INCREMENT ORDER RIGHT FOR A USER WHO WANTS EIGHT WORKING ENCODERS SOON?
No. The first deliverable here is the hardest one — full 20,223-byte-record recall through juno_bank_apply, a 29 KB address map, a generator, per-rate boot images. An encoder does not need any of it. An encoder needs juno_apply_param (src/juno_apply.c:321-334: one curve lookup, one cell write) on the shared tile, the blob-LEAF expansion from gui/juno_bridge.c:326-340, and a targeted coefficient update. That is a far smaller path and it exercises the address map on the handful of cells eight encoders actually reach. And nothing the user can hear arrives until a note-on works on the device, which is not in this design at all. Suggested order: (a) note-on/off through eb_alloc into the per-voice cells plus a targeted rebuild — the user can play; (b) one encoder → one binding → juno_apply_param → rebuild — the user can turn a knob; (c) full preset recall as designed; (d) patch write. As written, the user gets a board that recalls presets it cannot play and cannot edit.

VERDICT: the recall mechanism is sound and should be kept. The design as a whole cannot be built as written, because §3.4's own conclusion ("chip B cannot recall while it plays") collides with the fact that playing a note requires exactly that rebuild.

### FATAL
- THE NOTE PATH IS ABSENT, AND IT INVALIDATES THE CENTRAL SIZING DECISION. §1.4 states without qualification that 'the five scatter cells are the whole per-voice story, and I proved it structurally.' That is true of RECALL only. src/juno_note.c writes eight further per-voice sites: 304 pitch (:160), 320 gate (:164, :249), 6864 VCF velocity and 9680 VCA velocity (:196-197), 1856 and 9824 (:200-201), 592 portamento gate (:305), and the aux latch 101504+v*32 (:238, :262). Six of those are read per voice by the builder — eb_coefs.c:264 (cvg_p28=304), :59 (k6864), :93 (c9824), :233 (k1856), :218 (glide k592) — and two by the state seed/mirror at :341-352 and :359-384. With ONE shared voice tile every sounding voice takes the last note's pitch and velocity. The per-voice scatter set is thirteen cells, not five, and the generator, boot image, memory table and gate all rest on five.
- CHIP B CANNOT SOUND A NOTE UNDER THIS DESIGN. §3.4 states, correctly and to its credit, that with chip B 539 cycles over budget 'chip B cannot recall while it plays', and parks the problem as a patch-change problem to be handled 'during a deliberately quiet moment'. But a note-on IS a coefficient change (cell 304 is the note's pitch, eb_coefs.c:264), and a note-on is by definition not a quiet moment. Combined with §3.4's own rule that chip A must recall from its own copy of the patch bytes and the link has no control channel, the design has no mechanism by which chip B's two or three voices ever receive a new note's pitch or velocity. That is END_GOAL items 2 and 4 together. The fix is identifiable and cheap — a targeted per-voice update of six floats instead of a 10,121-instruction full rebuild — but it is not in the design, is not priced, and is not gated.
- THE GATE IS STRUCTURALLY BLIND TO THE CLASS OF DEFECT IT ALREADY CAUGHT ONCE. gate.c never issues a note event. §4.2's fourth tooth found that voice 0's scatter cells must not live in the shared tile, or voice v's write lands on voice 0 and the boot default survives. The identical hazard exists for all eight note-written cells above, and no case in the 384 can see it. The design cites tooth 4 as evidence the gate is strong; it is equally evidence that this exact hazard is the one the harness attracts, and the harness stops one step short of the place it recurs.

### OPTIMISTIC
- 'Eight blocks is 46.4 ms of latency between the knob and the sound — inaudible as a delay' (§3.5). Priced against a knob, applied to a note. A note-on requires the same rebuild, and 46 ms of note latency is not inaudible; it is roughly the threshold at which players report the instrument feeling detached. Neither figure has been heard.
- The 90,000-cycle planning number is a per-BURST figure and is presented as if it settled headroom. No sustained RATE is anywhere in the design. The pump as written caps rebuilds at one per eight blocks, i.e. ~21/s; an encoder emits 50-200 detents/s and a fast chord is three note-ons inside one block. There is no coalescing policy, no queue depth, and no stated maximum sustained parameter-change rate — which is what END_GOAL item 4 actually constrains.
- 'PSRAM impact is ZERO' (§2) is true of the recall structures and is a good decision. It is quietly not true of a patch change, which can switch DELAY TYPE or EFFECT TYPE and thereby change which of the nine PSRAM rings is live (S3L_RING_LEN[9], esp32s3/main/s3_listen_meta.h). Those rings are caller-owned, are not double buffered, and §3.1's argument that double buffering makes the joint-set analysis moot does not reach them.
- The coefficient-buffer arithmetic does not close. The shipping blob layout gives eb_render_coefs at 18,788 bytes (S3L_COEF_SZ, s3_listen_meta.h) and the design's own hoist saves 5*1,028 = 5,140, giving 13,648 — not the 14,188 quoted in §2. A 540-byte unexplained delta in a table that is used to claim 40% of free internal SRAM. Probably a differing EB_NUM_VOICES between the two figures; say which.
- 'chip A has roughly 1,800 cycles/sample spare' is carried in from an earlier measurement and is spent once, on the patch burst. It is not re-spent against the note-rate rebuilds, the bend/mod-wheel stream, or an arpeggiator firing sixteenths, all of which land on the same core.

### UNREAD
- The host half of the gate (the reference program under scratchpad/cells/host) — I read the device half, gate.c, in full, but not the reference it is diffed against. The claim 'ONE tree, two programs' is therefore READ-of-one-side only from my position.
- The executed 343-cell trace and the claim that randomising every record nibble found all 343 — I confirmed the gate's trial-1 nibble randomiser exists (gate.c:32-33) but did not re-run the trace.
- The Xtensa measurement behind '4 instructions, MEASURED' for the folded constant-offset access, and the 27-instruction / 14.2-probe array-loop counter-measurement. Load-bearing for §1.5 and unverified here.
- The 210,480-byte flash figure for recall code, and the 126,444 attributed to juno_curve.c.
- Whether the design's ebdev_scatter() handles voice indices 6 and 7. juno_apply_condition loops v=0..7 (src/juno_apply.c:478) and juno_apply_unison_spread likewise (:500), while gate.c sizes DS.scat at EBDEV_NV entries with EB_NUM_VOICES=6. I did not read ebdev.c to see whether the two extra voices are dropped, clamped, or trapped.

### MISSING
- THE LIVE SINGLE-PARAMETER EDIT — the encoders themselves. eb_recall_param() appears once, in the §1.3 file table, and is never described, priced or gated. It is not a small variant of full recall: gui/juno_bridge.c:315-345 expands the blob LEAF (HPF blob 38 = 4 binding rows, PORTAMENTO = 2), needs the patch's recalled HPF TYPE (juno_bridge.c:70-75 — the port's TYPE=0 curves were wrong on 10 TYPE=1 patches), replicates the value to all voices, bumps eb_coef_gen, and deliberately does NOT re-seed voices or re-apply CONDITION (:305-314) because doing so 'snapped the sound' on any live move mid-note. Running juno_bank_apply for an encoder detent reproduces exactly that defect.
- THE RECALL-TIME STASH. gui/juno_bridge.c:58-89 keeps lfo_rate_byte, dly_time_byte, dly_sync, dly_type, hpf_type, last_condition and host_bpm from the recall, because live edits and tempo changes need them. The device design has a 4 KB working record and no equivalent struct. Without it, HPF, PORTAMENTO, tempo-synced LFO and tempo-synced DELAY are not correctly editable.
- TEMPO, AND EVERYTHING SYNCED TO IT. juno_apply_lfo_tempo and juno_apply_delay_tempo are recomputed from the host BPM (juno_bridge.c:896-920). gate.c:43 calls the first with a hardcoded 128.0f and never calls the second at all, so tempo-synced DELAY is both unimplemented on the device and untested in the gate. The device has no tempo source: no MIDI clock, no tap, no internal clock UI. The arpeggiator on top of that needs carp's transport (src/carp.c:406, 446, 486-488), which uses double arithmetic and a 64-bit divide on a chip with neither in hardware.
- CONTINUOUS CONTROLLERS. Pitch bend and mod wheel write the live amount cells 4112 and 7456 (src/juno_apply.c:434-437), and 4112 is inside the mod coefficient block (eb_coefs.c:40) while 7456 is inside the VCF CV block (:69). A bend is a stream at 100+ messages/s, not an event. At the pump's ~21 rebuilds/s it is a staircase. Aftertouch, expression and sustain are not mentioned either.
- GLOBAL VOICE INDEX ACROSS THE TWO CHIPS. The firmware already carries S3L_VOICE_LO (esp32s3/main/juno_s3_listen.c:505, 633, 664), so a chip already knows it owns a voice RANGE. CONDITION scatter is per-voice DISTINCT by design (src/juno_apply.c:472-484, COND_TUNE_SCAL[v]/COND_FINE_SCAL[v]/COND_GAIN_SCAL[v]) and so is the UNISON spread (:487-500). eb_render_coefs_build indexes 0..EB_NUM_VOICES-1 (eb_coefs.c:11, :19). Nothing in the design maps a chip's local voice slot to a global voice number, so chip B builds global voices 0..1 rather than 4..5 and both chips deal the same detune and re-level scatter. The gate runs one 6-voice configuration; the 4+2 split it must actually ship in is untested. Related and also unrecorded: with 6 voices and eight CONDITION scalars, WHICH six the fork keeps is an audible decision nobody has written down.
- STATE, AS OPPOSED TO COEFFICIENTS, AT PUBLISH TIME. eb_coefs.c:381-384 says in its own comment that a coefficient rebuild must invalidate s->dco_live_seeded 'or the voice keeps last patch's non-pitch DCO fields'. §1.8 and §3.1 describe publish as one pointer swap of the coefficient buffer and never mention it. eb_render_state_seed (eb_coefs.h:37-41) and eb_render_events_mirror (:43-56) are unmentioned anywhere in the design; the second is precisely the note-event bridge, and it is per-voice.
- FX RE-INITIALISATION ON A PATCH CHANGE. A new patch can change DELAY TYPE, EFFECT TYPE and chorus mode, i.e. which dispatch arm runs and which of the nine rings is live (S3L_RING_LEN[9]). Nothing states what happens to ring contents, read/write pointers, the 34-tap reverb array or the chorus BBD state at the moment of the swap. §3.1's double-buffer argument covers the coefficient struct only.
- THE EDIT BUFFER, AND THEREFORE PATCH WRITE. §1.7 copies the flash template plus 132 bytes into a RAM working record at each recall. Nothing says the working record is UPDATED by every live edit. Without that, after twenty encoder moves the sound lives in cells and the 132 bytes still describe the patch as loaded — so 'save' saves something the user is not hearing. Also absent: the storage medium and its wear/atomicity, the user-bank format and size, a modified flag, and compare/revert.
- SYSTEM (NON-PATCH) PARAMETERS HAVE NO HOME. MASTER TUNE is cell 4448, written by init and marked 'set by init; DO NOT write' (src/juno_note.c:99), and is not one of the 132 bytes — so the instrument cannot be tuned to anything else. The Kbd Velocity SW policy (gui/juno_bridge.c:857; the plugin's default forces every note to velocity 100) has no device switch. The MODULATION family, indices 312-317, identity only at offset 0 (src/juno_mod.c, juno_bridge.c:427), has no store. END_GOAL item 5 says every parameter; the design carries one 132-byte store and stops.
- POWER-ON BEHAVIOUR BEYOND THE CELL IMAGE. The baked post-init+prepare image is the right idea and is measured. Unstated: which patch is loaded at power-on, whether the instrument is silent or holds the last patch across a power cycle, and how the two chips agree on that before the link is up. Related, and the sentence the design should lead with: today's firmware has no note path at all — juno_s3_listen.c:889 and :1001 memcpy captured note-on and note-off STATE snapshots and replay them at S3L_HOLD_FRAMES/S3L_REL_FRAMES. Device recall on top of that is still not an instrument.
- NO RENDERED COMPARISON ANYWHERE. The coefficient-byte gate is the right primary standard and I would not replace it. But there is no case that recalls on the device, renders N samples, and nulls against the host — which is the only check that covers the state seed, the FX rings, the publish boundary and the note path at once. §4.3's device CRC is computed after a recall and never after a note, which is where the per-voice hazard lives. eb_render_state is never CRC'd at all.
- TWO-CHIP AGREEMENT AND FAILURE POLICY. The design requires two separately flashed binaries to produce bit-identical coefficients, but names no mechanism to prove the two flashed images agree at runtime — the boot banner prints an image sha256 per chip and nothing compares them. §4.4 mutes on an unmapped cell, which is right; unstated is what the OTHER chip does when its partner mutes (two chips disagreeing about whether they are playing is worse than both stopping), how a corrupt 132-byte set is rejected before it reaches juno_bank_apply, and what any of this looks like on the LCD.
- THE UI LAYER THE USER WILL ACTUALLY TOUCH. Encoder-to-parameter mapping, the current value to display, the parameter name, and the units. The pieces exist host-side (juno_param_name / juno_param_blob / juno_param_offset, src/juno_apply.c:296-314, and the working record already holds the displayable byte at 2*blob) so this is cheap — but it is the visible half of 'eight working encoders' and the design does not name it.
