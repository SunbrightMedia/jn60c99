# MEMORY LEVER — measured verdict, 2026-08-01

**Headline, and the single most useful fact found so far:** the engine touches
620 distinct 4-byte cells per voice per sample, and **every one of them sits on
its own 16-byte boundary** — the plugin's SSE layout carried over verbatim. A
Cortex-M7 cache line is 32 bytes, so it carries at most 2 useful cells.
**75.6% of every line fill is wasted.**

Memory stall is **54–77% of the 93,288 cyc/sample, best estimate 70%**.
Cross-validated: that implies 7.8–8.9 cycles per access, and E4 measured SDRAM
sequential at **8.79 cyc/access** on silicon. Two independent methods agree.

**The lever is worth ~2× (1.4–2.5×), with a hard ceiling of 3.1–4.3× if memory
were free.** It is necessary and NOT sufficient. 11.19× is required, so **3–5×
must still come from cutting the ~29,700 instructions per sample.**

The good news is the size: compacted to 4-byte stride, the hot set is
**~21 KB** (620 cells x 4 B x 8 voices = 19.8 KB, plus ~1.3 KB of master cells).
That fits DTCM (128 KB) with room to spare. The FX delay/reverb buffers stay in
SDRAM — only ~130 accesses/sample reach them and they stream sequentially.

This CONFIRMS the withdrawn inference was wrong to dismiss memory, and also
shows the replacement hypothesis was too hopeful: E3's 1.05× is explained by
effective line reuse of ~1 (85.2 KB of lines per sample against a 16 KB L1), not
by memory being cheap.

Generated by a 9-agent workflow, 0 errors. Host instrumentation is MEASURED;
ARM instruction counts are STATIC; the speedup figures are MODELED on E4's
SILICON per-access costs. No silicon confirmation of the lever itself yet.

## 1. What fraction of 93,288 cyc/sample is memory stall?

**Honest answer: UNMEASURED on silicon. The estimate is 54-77%, best estimate 70%. Label: ESTIMATE, built from MEASURED access counts + STATIC ARM instruction counts + SILICON E4 per-access costs.**

The inputs are solid; the conversion is not.

| Quantity | Value | Label |
|---|---|---|
| State accesses per sample | 9,850 (6,943 ld / 2,907 st) | MEASURED (host instrumentation) |
| Distinct 4B cells / sample | 5,196 | MEASURED |
| Distinct 16B blocks / sample | 5,196 — **equal to the cell count** | MEASURED |
| Distinct 32B cache lines | 2,662 = 85.2 KB | MEASURED |
| Useful density per line fill | 24.4% | MEASURED |
| Accesses inside `[176, 84272)` | 92.5% | MEASURED |
| ARM instructions / sample | ~29,700 (~8,100 memory) | STATIC (`-O2 -mcpu=cortex-m7`) |
| Observed CPI | 3.14 | derived from SILICON + STATIC |
| Implied cyc per memory access | 7.8-8.9 | derived |
| E4 SDRAM sequential | 8.79 cyc/access | SILICON |

The cross-check is the strong part: the implied per-access cost lands on E4's measured SDRAM number. The weak part is the assumed 1.0-2.0 cyc/instr for the ~21,600 non-memory instructions. That assumption alone sets the whole 54-77% width, and nobody measured it on an M7.

**The single most damaging structural fact, and it is MEASURED, not modelled: every touched cell sits on its own 16-byte boundary.** This is the plugin's SSE layout carried over verbatim. A 32-byte M7 line carries at most 2 useful cells. That also explains E3's 1.05x with no contradiction: 85.2 KB of lines per sample against a 16 KB L1 gives effective reuse ≈1, so cache on and cache off are nearly the same.

Do not model this further. Measure it (§5).

## 2. Which relocation approach wins?

**SPLIT POOL wins. VOICE RELOCATE is its first stage, not a competitor.**

They are the same move at two scopes. Voice Relocate moves `[176,84272)` (92.5% of accesses). Split Pool moves `[0,102800)` — the same block plus the shared noise block, the aux latches, the chorus BBD rings and the low master clusters — for the same single boundary comparison and no extra runtime cost.

Reasons Split Pool wins:

1. **One boundary, not a table.** Every per-sample non-streaming cell is below 102,800 and the first 2 MB delay ring begins exactly at 102,800 (STATIC, exhaustive literal scan). The boundary is free.
2. **It removes Voice Relocate's silent-failure mode.** Voice Relocate splits `base` into three regions inside `voice_render` (main block, shared noise at 84272, aux latch at 101504+32v) and leaves 8 master taps at `10672+v*10512` pointing at the old array. That reads stale floats and does not crash. Split Pool keeps all of those on the same side of the boundary, so the bug cannot occur.
3. **Zero codegen cost.** `juno_r0`/`juno_r1` are link-time symbols and every offset in `voice_render.c` is provably below the boundary, so the comparison folds at compile time. No branch, no table load.

**Factor: MODELED 1.4x-2.5x, working number ~2.0x.**
`1 / (0.30 + 0.70·0.045 + 0.70·0.955/k)`, k from E4 (1.76x sequential, 6.26x scattered; this pattern is 16B-strided so it sits between). k=6.26 → 2.19x; mem_frac at the 0.77 end → 2.49x; k=1.76 → 1.39x.

**Hard ceiling with memory entirely free: 3.1x-4.3x** (93,288 ÷ 21,600-30,200 arithmetic cycles). That ceiling needs only the instruction count and the SILICON total, not the CPI assumption, so it is the most reliable number in this report.

**Fit (STATIC, from `libDaisy/core/STM32H750IB_flash.lds`):** `[0,102800)` = 100.4 KB. DTCM is 128 KB → fits with 28,272 B spare, but that must hold the stack. AXI SRAM is 512 KB → fits trivially but costs 12.02 vs ~1-2 cyc/access. Fallback if the stack will not yield: 82 KB voice blocks to DTCM, the 18 KB remainder to AXI. The five 2 MB delay lines stay in SDRAM — they stream, and sequential SDRAM is 8.79 cyc/access, not 75.34.

## 3. Does anything change arithmetic?

**No. Neither approach changes one float operation, one operand, or one order of evaluation.** They change only how a byte offset becomes a pointer. IEEE-754 results are address-independent and 16-byte cell alignment is preserved because the low region moves as one block with no compaction.

Consequences, and they matter:

- **The test is exact zero, not −90 dB.** `tools/trackb/null_ab.py` must report EXACTLY 0 differing samples. Anything else means the relocation is wrong. That is a far stronger gate than the sonic-identity machinery.
- **The Track B sonic gates are not needed for this change,** and neither is the STANDING WARNING about the 15 BLIND Chamberlin SVF assignments. Blindness only matters when arithmetic changes. No module is rewritten.
- **It would be admissible in `src/` under the project's own rule.** Land it in `native/` behind `JUNO_SPLIT_POOL` anyway: the risk here is aliasing, lifetime and linker sections, not numerics, and `src/`'s value is that it is frozen. With the symbol undefined the macro is the textual identity, so host/x86/WASM builds produce the same object code they do today.
- **Cost of that: the host gates never exercise the split path.** Only ARM `null_ab` and E1 golden-on-silicon can prove it. Re-run `tools/embed/arm_golden.sh` and E1 **with the split active**.

**What is NOT bit-exact-preserving, and is therefore not in this report's scope:** cell compaction (packing 620 cells to 4-byte stride, ~21 KB total) does not change arithmetic either, but it does change every offset, so it needs the offset-remap tooling and a full re-derivation. The instruction-count reduction that §4 requires — scratch-cell elimination, triangle LUT, block hoisting — *does* change arithmetic, and those need the sonic gates and the blind-scenario work first.

## 4. Does 11.19x come into view? Blunt answer: no.

**No. Not with the memory lever, and not with the memory lever plus every measured arithmetic lever.**

Multiply the best cases:

| Lever | Factor | Label |
|---|---|---|
| Split Pool relocation | 2.0x (band 1.4-2.5) | MODELED |
| All measured arithmetic levers, stacked optimistically | ~1.3x | MEASURED individually |
| Combined | **~2.6x** | MODELED |
| Required | **11.19x** — or ~34.5x if the wrap correction stands | SILICON |

The measured arithmetic levers do not add up: block hoisting 2.8% (ceiling 17.4%), idle-voice skip 0% at full polyphony, triangle LUT ~11% STATIC, FTZ 2.4%. None approach the 3x-5x that would have to come from instruction reduction after a perfect memory fix.

**Polyphony is dead as a lever and 6 voices does not help.** The idle floor is 85,137 of 93,288 = 91% (SILICON), and under the wrap correction it becomes ~97%. 4 voices is 9% cheaper than 8. The permitted 6-voice fallback buys ~5%. It changes nothing about the gap and must not be treated as a plan.

**What this means, stated plainly.** The 11.19x target requires cutting ~29,700 instructions/sample to under ~2,700 *and* making memory free. That is not an optimization programme; it is a different engine. Track B's premise — sonic identity instead of bit-exactness, rewriting modules in `native/` — is the only path that could produce those numbers, and its own STOP rule S1 does not fire, so it stays alive. But the honest position today is: **the Daisy Seed at 400 MHz has not been shown to be capable of 8 voices plus all FX at 48 kHz, and the measured levers do not reach it.** P2 is a real decision.

The corrected E2 could make this worse by 3x. Flash it before anything else.

## 5. The exact next experiment: E6 + E7

Two experiments, in this order. E6 costs no engine change and settles §1. E7 costs one pointer and settles §2.

### E6 — measure the memory fraction directly, by replaying the real access pattern

Replay the MEASURED offset trace (`scratchpad/memtrace/acc.txt`, 9,850 rows) as pure loads and stores with no arithmetic, once against the SDRAM state and once against an AXI-resident copy of the low 100.4 KB. The difference between them, per access, is the lever. The absolute cost of the SDRAM pass, divided by 93,288, is the memory fraction.

Generate the trace table first (offsets under 102,800 only; the rest stay SDRAM either way):

```sh
python3 - <<'EOF' > daisy/memtrace_table.h
rows = [l.split() for l in open('scratchpad/memtrace/acc.txt')]
rows = [(int(o), int(s)) for o, s in rows]
print("/* MEASURED per-sample access trace, host instrumentation. */")
print("#define MT_N %d" % len(rows))
print("static const uint32_t mt_off[MT_N] = {%s};" %
      ",".join(str(o) for o, _ in rows))
print("static const uint8_t  mt_st [MT_N] = {%s};" %
      ",".join(str(s) for _, s in rows))
EOF
```

Add to `daisy/juno60_daisy.cpp`:

```c
/* ================= E6: how much of the cost is memory? ==================
 * Replays the MEASURED 9,850-access-per-sample trace with NO arithmetic.
 * Pass A: against the 12 MB SDRAM state.  Pass B: the low 100.4 KB served
 * from AXI SRAM instead.  A - B is the split-pool lever, per access, on
 * SILICON.  A / 93288 (or / the wrap-corrected E2) is the memory fraction.
 * volatile is load-bearing: it stops the compiler hoisting the loads. */
#include "memtrace_table.h"

#define E6_R0   102800u
#define E6_REPS 4096                    /* 4096 * 9850 acc ~ 40 M accesses */

static uint8_t g_axi_lo[E6_R0] __attribute__((aligned(32)));  /* -> .bss = AXI */

static uint32_t e6_pass(uint8_t *lo, uint8_t *hi)
{
    span s = {0, 0, 0};
    uint32_t m0 = System::GetNow();
    for (int r = 0; r < E6_REPS; ++r) {
        uint32_t t0 = cyc();
        for (int i = 0; i < MT_N; ++i) {
            uint32_t o = mt_off[i];
            volatile float *p = (volatile float *)
                (o < E6_R0 ? lo + o : hi + o);       /* hi is the 12 MB base */
            if (mt_st[i]) *p = (float)i; else (void)*p;
        }
        uint32_t d = cyc() - t0;
        if (d > 0x80000000u) g_wrap_suspect = 1;
        s.cyc += d;
    }
    s.ms = System::GetNow() - m0;
    /* report() cross-checks DWT against the tick, same as E2/E3. */
    report("E6 pass", s, (uint32_t)E6_REPS);
    return (uint32_t)(s.cyc / (uint64_t)E6_REPS);     /* cycles per sample */
}

static void e6_memory_fraction(void)
{
    LOG("E6: memory-only replay of the MEASURED access trace");
    sdram_ensure();
    uint8_t *st = (uint8_t *)malloc(JUNO_STATE_BYTES);   /* SDRAM pool */
    if (!st) { LOG("  E6: alloc FAILED"); pool_report("E6"); return; }
    memset(st, 0, JUNO_STATE_BYTES);
    memset(g_axi_lo, 0, sizeof g_axi_lo);

    uint32_t a = e6_pass(st, st);            /* all SDRAM  */
    uint32_t b = e6_pass(g_axi_lo, st);      /* low in AXI */

    LOG("  E6 SDRAM  %6d cyc/sample  (%d cyc/access over %d accesses)",
        (int)a, (int)(a / MT_N), MT_N);
    LOG("  E6 AXI-lo %6d cyc/sample  (%d cyc/access)", (int)b, (int)(b / MT_N));
    LOG("  E6 lever  %d.%02dx on the memory component",
        (int)(a / (b ? b : 1)), (int)((float)a / (float)(b ? b : 1) * 100) % 100);
    LOG("  E6 memory fraction of E2 8v = %d%%  (E2 8v = %d cyc/sample)",
        (int)(100.0f * (float)a / (float)(g_e2_8v.cyc /
             ((uint32_t)E2_RATE / 2))), (int)(g_e2_8v.cyc /
             ((uint32_t)E2_RATE / 2)));
    free(st);
    pool_report("E6 done");
}
```

Call it after `e3_...()` in `main()`, so `g_e2_8v` is populated.

**What E6 settles, and what it does not.** It converts "54-77%, ESTIMATE" into a SILICON number, and it prices AXI-vs-SDRAM on the engine's *actual* pattern rather than E4's synthetic one. It does not measure the non-memory CPI directly — but it no longer needs to, because the memory side becomes measured and arithmetic is then the remainder.
