# JUPITER-8 — SCOPE AUDIT (what the gates actually prove)

Written 2026-10-12, in the JX-3P's format (jx3p/docs/SCOPE_AUDIT.md) and under docs/PORT_COMPLETENESS_CHARTER.md:
every dimension along which a gate's scope can be narrower than its claim, with its MEASURED status. A row is CLOSED
only when a named gate run says so. "The JUPITER-8 is bit-exact" means nothing without this table.

The port is the plugin's own machine code, LIFTED (jp8/tools/jp8_lift.py -> jp8/src/jp8_host_lift.c, then
jp8_fast.py and jp8_xlane.py for the product build), run by jp8/src/jp8_host.c on the memory the host oracle had
before the host learned its rate (jp8/docs/HOST_LAYER.md). So a row is about two things: REACH (did a drive make the
plugin run that code, so that it is lifted at all -- code outside the reach is a trap, never a silent difference) and
GRADING (did a gate compare that behavior word for word against the oracle).

| # | Scope dimension | Status | Evidence |
|---|---|---|---|
| 1 | Parameter coverage | **OPEN -- the v7 drive closes it** | Census: 226 controller parameters (96 panel + CC 0..127 + aftertouch + bend; jp8_controller_census.py -> jp8/gen/jp8_controller.json) and every panel parameter's POSITIONS from the plugin's own getParamStringByValue at k / 256 (jp8_param_positions.py -> jp8/gen/jp8_param_positions.json: 37 switches of 2..24 positions, 59 continuous). The v6 drive moves ~10 of the 96 by host automation (two per patch, MASTER TUNE, a swept one, a learned one); the 4 patches' recalls set the rest to those patches' values. The v7 drive (jp8_host_seq.sweep_steps, 1,358 steps) moves ALL 96: every switch position, five values of a continuous one, from a fresh patch load each, a chord sounding, bend and mod wheel moving. |
| 2 | Effects (3 units x 6 types) | **OPEN -- the v7 drive closes it** | EFFECT TYPE, DELAY TYPE, REVERB TYPE: 6 positions each (census). v6: the 4 patches' own settings only. v7: each type of each unit with the levels up, that unit's parameters at every position / three values under it, a chord re-struck per type, a tail. |
| 3 | Arpeggiator | **OPEN -- the v7 drive closes it** | ARPEGGIO SW, MODE (6), RANGE (6), TEMPO SYNC (2). v6: never on. v7: every mode x range, free and synced to a running host clock (ppq advancing per block), the switch off under held keys. Host transport states (stopped, loop, tempo changes) are NOT in it. |
| 4 | Note allocation | **OPEN -- the v7 drive closes it** | v6: a chord of ten keys on eight voices (stealing), release, velocities 0.3..1.0, keys inside blocks. v7 adds ASSIGN MODE (4) x LEGATO x PORTA TYPE with overlapping keys and portamento, KEY HOLD across a release, keys on MIDI channels 5 and 15 and a note-on of velocity 0. |

| 18 | NaN / denormal parity, the MXCSR | **CLOSED on the graded drive (x86-64 hardware and software floats); AArch64 on the render only** | The guest MXCSR is modeled exactly (playbook 241): stmxcsr reads back what the plugin loaded, never the host CPU's sticky flags (the CRT reads them, _statusfp 0x7A4528); the host runs at the guest's FTZ / DAZ with every exception masked; the oracle's thread starts at 0x1F80 as a Windows thread does (it started at Unicorn's 0, so the CRT's float error handler took its unmasked path -- only the graded stack showed it). The oracle's own float modes, MEASURED (jp8_unicorn_fp_probe.py): DAZ yes, FTZ NO, no sticky flags. Software floats (JP8_SOFTFP=2: DAZ / FTZ from the guest's MXCSR, in C) EXACTLY 0 on the v7 drive, stack included; with no software flush (tooth T12) the memory after differs (denormal inputs reach the engine's state). AArch64 (gcc 13 cross, -std=c99, static, qemu-aarch64 8.2.2, SOFTFP=2): the render CLI's WAV and plan byte-identical to the graded x86 render (not the gate's drive). Speed in software floats: ~3.7 s per second of audio on x86 (5.6x the hardware build). |
| 19 | ISO C99 | **CLOSED** | every gate build is gcc -std=c99 -pedantic-errors; the threads are a separate platform layer (_POSIX_C_SOURCE). |
| 20 | Mutation reach (charter section 4) | **OPEN -- 5 survivors on the v6 drive** | jp8_mutation_gate.py (one build, 41 one-instruction slips drawn with seed 1 from the lift's reach -- float add / sub / mul and a store's low bit -- each slip COUNTING how often it ran and how often it changed a value; controls: no slip EXACTLY 0, the T1 site KILLED). On gate8's build and drive v6 at 48000 (job jp8_mutgate2, jp8/logs/mutation_v6_seed1.log): KILLED 22; UNREACHED 10 (the 4-patch drive never runs them -- row 5); EQUIVALENT 4 (ran 5,616-74,293 times, never changed a value); SURVIVED 5 -- each changed every value it made and nothing graded saw it: a voice state store at 0x39e182, a voice temporary 0x3bc0e7, two in the effects' function f_38dc60 (0x38e6e6, 0x3906b1), a stack argument 0x382de7 the callee ignores on this path. The v7 sweep (every effect and filter setting) is the gate to write; re-run after it. |

| 22 | A playable product | **PARTIAL -- an offline renderer, graded; no live app yet** | jp8/apps/jp8_render.c (ISO C99): the shipped template (jp8/gen/jp8h_template.bin.gz: raw sha256 f43e2d35..., the oracle's template after the MXCSR fix (it was a30f59c6...); the host gate's new stage 2b checks it on every run from the next one, tooth T11), a factory patch and a MIDI file (format 0 / 1, tempo map) -> a float WAV through the lifted process(). jp8/apps/render_check.sh: the oracle replays the CLI's plan (every block's events and points) -- patch 2, 5.56 s (a chord, a tempo change, CC 1 / 7 / 11 / 64, bend, pressure, channel 3, a note-on of velocity 0): EXACTLY 0, 267,001 frames; one flipped bit is seen (jp8/logs/render_check_patch2.log, on the v7 lift). | 23 | A denormal RESULT (FTZ) | **OPEN -- the oracle cannot show it** | The plugin runs process() at FTZ + DAZ (its ScopedNoDenormals); Unicorn 2.1.4 implements DAZ but never flushes a result (PROVEN, jp8_unicorn_fp_probe.py; the JX found it first, playbook 120). The hardware build flushes as the plugin on a PC does; the gates are EXACTLY 0 because no graded drive makes a denormal result (the flush-removed tooth T12 bites through denormal INPUTS). A drive that made one would separate the plugin on a PC from its oracle: the port follows the PC (hardware, SOFTFP=2); SOFTFP=1 models the oracle (DAZ only). |
